# Slotbook Final Engineering Audit

**Audit revision:** `66a31631a757e0d26e7926fbbcb1d4339ac69452`
**Scope:** implementation, database schema/migration, API authorization, scheduling, tests, and submission documents.
**Changes made:** this report only. No application code or database data was changed.

## Executive summary

Slotbook has a sound core for **per-event-type** capacity: hold creation and rescheduling use PostgreSQL transactions, lock the event row, evaluate current holds/confirmed bookings, then write the booking in the same transaction. Confirmation and cancellation lock the booking row. Database time is used for five-minute expiry, idempotency results are transactionally stored, and booking instants are UTC. The previous QA milestone recorded 16 PostgreSQL integration tests and 15 Playwright cases passing; this audit did not rerun database-backed suites.

The most important correctness concern is that the locking and conflict query are scoped to one `EventType`, not the host. A host with two event types can therefore receive bookings for the same instant from both event types. If the product's availability represents one host calendar—as the assignment's overlap requirement suggests—this is a **high-severity booking correctness defect**. The intended policy should be confirmed if event types are supposed to be independently bookable resources.

Security review found no SQL-injection path in the inspected application queries and no unprotected host management handler. The host session cookie is HTTP-only, SameSite=Lax, Secure in production, and signed with an eight-hour expiry. The notable security gaps are missing rate limits on login and public booking endpoints, and long-lived bearer management links that expose guest PII and permit booking changes. These are abuse/privacy concerns, not evidence of an existing account takeover.

## Architecture overview

- Next.js App Router pages and route handlers; Zod validates API inputs.
- Prisma/PostgreSQL models hosts, event types, weekly rules, date overrides, bookings, idempotency records, and notification sink rows. See [`schema.prisma`](../prisma/schema.prisma#L10) and the SQL constraints/indexes in [`migration.sql`](../prisma/migrations/20261105192000_initial/migration.sql#L19).
- [`booking.ts`](../src/lib/booking.ts#L109) generates host-local slots, applies date overrides, notice/horizon limits, DST rules, overlap buffers, and capacity.
- [`booking-service.ts`](../src/lib/booking-service.ts#L54) owns transactional booking lifecycle operations and PostgreSQL row locks.
- Host authentication uses bcrypt and signed stateless cookies in [`auth.ts`](../src/lib/auth.ts#L15); protected API handlers resolve the signed host ID and constrain management operations to that host.
- Unit tests cover pure scheduling/validation/auth logic; PostgreSQL integration tests cover transaction races and host management; Playwright covers real guest and host flows in Chromium, Firefox, and WebKit.

## Phase 1 — Booking reliability and database correctness

### Findings

| ID | Severity | Finding and evidence | Assessment / reproducible scenario |
|---|---|---|---|
| B1 | **High** | **Bookings can overlap across distinct event types for one host.** `lockEvent` locks only the requested event row ([`booking-service.ts:54`](../src/lib/booking-service.ts#L54)); `activeBookings` filters by `eventTypeId` ([`booking-service.ts:95`](../src/lib/booking-service.ts#L95), [`booking-service.ts:98`](../src/lib/booking-service.ts#L98)). The public slots query also loads bookings from only the requested event type ([`slots/route.ts:41`](../src/app/api/hosts/%5Bhost%5D/events/%5Bslug%5D/slots/route.ts#L41), [`slots/route.ts:46`](../src/app/api/hosts/%5Bhost%5D/events/%5Bslug%5D/slots/route.ts#L46)). | **Real if the host is a single bookable resource**, as is conventional for this app. Create two event types for one host with overlapping hours; submit holds for the same UTC instant, one per event type. Each sees no booking in its own event and both can succeed, including concurrently because they lock different rows. The current concurrency suite tests same-event capacity but not cross-event overlap ([`booking-concurrency.spec.ts:91`](../tests/integration/booking-concurrency.spec.ts#L91), [`booking-concurrency.spec.ts:103`](../tests/integration/booking-concurrency.spec.ts#L103)). Recommend host-level serialization plus conflict checks against that host's other event bookings, while preserving group capacity within one event. |
| B2 | **Medium** | **Configuration edits do not reconcile existing bookings.** Event type updates validate the new values and then update the row without checking existing reservations ([`host-management.ts:296`](../src/lib/host-management.ts#L296), [`host-management.ts:309`](../src/lib/host-management.ts#L309)); capacity is accepted down to 1 ([`host-management.ts:11`](../src/lib/host-management.ts#L11)). Schedule and override edits likewise change future availability without checking overlapping confirmed bookings ([`host-management.ts:137`](../src/lib/host-management.ts#L137), [`host-management.ts:186`](../src/lib/host-management.ts#L186), [`host-management.ts:207`](../src/lib/host-management.ts#L207)). | **Real operational consistency risk; intended product policy is unspecified.** With three confirmed guests in a capacity-three group, reduce capacity to one; the update succeeds and leaves three confirmed guests in that interval. Similarly, mark a booked date unavailable: the confirmed booking remains, but the schedule no longer offers that time. The system does not cancel existing bookings, which avoids data loss, but does not warn or prevent conflicting configuration. Define whether to reject, warn, grandfather existing bookings, or notify guests. |
| B3 | **Medium** | **Active booking reads scan all active/history rows for an event instead of a bounded time range.** `activeBookings` filters only by event ID and status ([`booking-service.ts:95`](../src/lib/booking-service.ts#L95)); the public slots API loads all confirmed and unexpired holds for the event before generating a maximum 31-day range ([`slots/route.ts:30`](../src/app/api/hosts/%5Bhost%5D/events/%5Bslug%5D/slots/route.ts#L30), [`slots/route.ts:46`](../src/app/api/hosts/%5Bhost%5D/events/%5Bslug%5D/slots/route.ts#L46)). | **Real scalability concern, not a current correctness failure.** As an event accumulates historical confirmed bookings, each slot request and hold/reschedule check fetches and iterates them even though old rows cannot overlap the candidate interval. Bound reads by candidate range plus buffers; add an index/query plan check at representative volume. |
| B4 | **Low** | **Expired status is mostly lazy and expiry has no notification event.** Capacity reads ignore holds whose expiry is not later than the DB timestamp ([`booking-service.ts:95`](../src/lib/booking-service.ts#L95)); an expired row is changed to `expired` only when confirmation is attempted ([`booking-service.ts:284`](../src/lib/booking-service.ts#L284), [`booking-service.ts:298`](../src/lib/booking-service.ts#L298)). That branch writes no `Notification`, unlike hold, confirmation, reschedule, and cancellation paths. | **Not a capacity bug:** expired holds stop consuming capacity without cleanup and the management page derives an expired display from `expiresAt`. The stored enum can remain `held` until an attempted confirmation, and consumers of the notification sink receive no expiry event. Add a worker only if persistent transition/event delivery is required by the assignment; otherwise document lazy expiry as the design. |
| B5 | **Low** | **Idempotency rows have no retention policy.** Every unique key is persisted with a globally unique constraint ([`migration.sql:110`](../prisma/migrations/20261105192000_initial/migration.sql#L110)); the booking service inserts/replays them transactionally ([`booking-service.ts:152`](../src/lib/booking-service.ts#L152)). | **Operational, not an immediate correctness issue.** Long-running public use grows the table without bound. Define a retention period longer than the retry window and prune safely; deleting keys too early can cause a late retry to create a second hold. |

### Verified design properties

- **Transaction/isolation:** booking operations use Prisma interactive transactions. No explicit `SERIALIZABLE` isolation level is configured; correctness for the same event relies on PostgreSQL row locks under the normal transaction isolation. `lockEvent` uses tagged `$queryRaw` with `FOR UPDATE OF e`; booking state changes use `FOR UPDATE` on the booking row ([`booking-service.ts:54`](../src/lib/booking-service.ts#L54), [`booking-service.ts:74`](../src/lib/booking-service.ts#L74)). The lock is effective for same-event contenders but does not coordinate distinct event types (B1).
- **Same-event capacity:** hold creation locks the event before reading current active bookings and inserting a hold ([`booking-service.ts:198`](../src/lib/booking-service.ts#L198), [`booking-service.ts:207`](../src/lib/booking-service.ts#L207)). Rescheduling follows the same event lock, excludes only its own booking from target capacity, then updates atomically ([`booking-service.ts:349`](../src/lib/booking-service.ts#L349), [`booking-service.ts:362`](../src/lib/booking-service.ts#L362), [`booking-service.ts:376`](../src/lib/booking-service.ts#L376)). This is a justified database-level strategy for a single event type; no JavaScript mutex is used.
- **Five-minute holds:** expiry is calculated from PostgreSQL `clock_timestamp()` and reset at insert/update time to exactly five minutes ([`booking-service.ts:86`](../src/lib/booking-service.ts#L86), [`booking-service.ts:238`](../src/lib/booking-service.ts#L238)). The integration suite checks remaining time against database time, forces expiry, verifies confirmation rejection, and confirms a replacement can hold the slot ([`booking-concurrency.spec.ts:156`](../tests/integration/booking-concurrency.spec.ts#L156)).
- **Expired/cancelled capacity:** reads include confirmed bookings and held bookings with `expiresAt > now`; the conflict calculation ignores cancelled, expired, and elapsed holds ([`booking-service.ts:95`](../src/lib/booking-service.ts#L95), [`booking.ts:215`](../src/lib/booking.ts#L215)). Cancellation marks the row cancelled in a transaction, releasing capacity. A stale public availability response can still race with a hold expiry, but hold creation rechecks with fresh DB time and can return `409`; this is an acceptable stale-read race.
- **Idempotency:** a unique key is inserted with `ON CONFLICT DO NOTHING`, then selected `FOR UPDATE`; payload hash mismatch returns `409`, while the successful response is written in the same transaction as the booking ([`booking-service.ts:152`](../src/lib/booking-service.ts#L152), [`booking-service.ts:166`](../src/lib/booking-service.ts#L166), [`booking-service.ts:266`](../src/lib/booking-service.ts#L266)). Concurrent retry coverage exists ([`booking-concurrency.spec.ts:141`](../tests/integration/booking-concurrency.spec.ts#L141)).
- **Confirmation races:** confirmation locks the booking row and requires `held`, so only one concurrent call can transition it to confirmed; an elapsed hold is changed to `expired` and fails with `409` ([`booking-service.ts:284`](../src/lib/booking-service.ts#L284), [`booking-service.ts:291`](../src/lib/booking-service.ts#L291)). An integration test asserts one success and one conflict ([`booking-concurrency.spec.ts:176`](../tests/integration/booking-concurrency.spec.ts#L176)).
- **Reschedule/cancel:** a failed reschedule throws before the update and rolls the transaction back; the existing interval stays intact. The integration suite verifies competing reschedules and a conflict preserving the old slot ([`booking-concurrency.spec.ts:120`](../tests/integration/booking-concurrency.spec.ts#L120), [`booking-concurrency.spec.ts:220`](../tests/integration/booking-concurrency.spec.ts#L220)). Guest cancellation defaults a missing reason to `"Cancelled by guest."`; supplied reasons are trimmed and bounded in [`cancel/route.ts:5`](../src/app/api/bookings/%5Btoken%5D/cancel/route.ts#L5). Host cancellation requires a 2–500 character reason and verifies booking ownership ([`host cancel route:10`](../src/app/api/host/bookings/%5Bid%5D/cancel/route.ts#L10), [`booking-service.ts:427`](../src/lib/booking-service.ts#L427)).
- **Timezones and DST:** host windows are resolved through Luxon/IANA zones; booking instants are `TIMESTAMPTZ`, overrides are local `DATE` values ([`schema.prisma:86`](../prisma/schema.prisma#L86), [`schema.prisma:63`](../prisma/schema.prisma#L63)). The slot builder rejects invalid zones/ranges, applies notice/horizon limits, and uses explicit DST candidate resolution ([`booking.ts:58`](../src/lib/booking.ts#L58), [`booking.ts:109`](../src/lib/booking.ts#L109), [`booking.ts:136`](../src/lib/booking.ts#L136)). Nonexistent and ambiguous starts are omitted; tests cover both New York DST transitions ([`booking.spec.ts:73`](../tests/unit/booking.spec.ts#L73)).
- **Buffers and group capacity:** each overlapping booking consumes one seat; the configured before/after buffers expand compared intervals ([`booking.ts:230`](../src/lib/booking.ts#L230), [`booking.ts:244`](../src/lib/booking.ts#L244)). This works for overlapping reservations within one event and is unit/integration tested; it does not solve B1 across event types.
- **Database constraints:** the migration enforces interval ordering, held expiry presence, positive capacity, range bounds, foreign keys, and relevant unique indexes ([`migration.sql:27`](../prisma/migrations/20261105192000_initial/migration.sql#L27), [`migration.sql:79`](../prisma/migrations/20261105192000_initial/migration.sql#L79), [`migration.sql:80`](../prisma/migrations/20261105192000_initial/migration.sql#L80)). Application bounds are stricter for some fields (e.g. capacity max 100, horizon max 365, notice max 43,200) than database checks. API writes are validated, but direct DB writes can bypass those upper limits; low-risk for this app but worth aligning schema and DB checks.
- **Notifications:** hold, confirmed, rescheduled, and cancelled events are inserted in the booking transaction, so a failed booking transition cannot leave a success-shaped event ([`booking-service.ts:246`](../src/lib/booking-service.ts#L246), [`booking-service.ts:314`](../src/lib/booking-service.ts#L314), [`booking-service.ts:379`](../src/lib/booking-service.ts#L379), [`booking-service.ts:412`](../src/lib/booking-service.ts#L412)). These are DB sink records only; no email is sent. Expiry is the exception in B4.

No high-impact CSRF exploit was identified in the inspected routes. Logout is a form POST and has no origin check, so cross-site forced logout is a possible low-impact nuisance. Add an Origin check/CSRF defense as defense in depth if the app gains cookie-authenticated form or non-JSON mutations. |

Payloads are not consistently `.strict()` across every route, but Zod strips/ignores unrecognized fields rather than passing them to Prisma. Request body size limits are not configured in application code. |

The E2E setup has one `$executeRawUnsafe` call with a fixed literal schema statement, not user-controlled input ([`global-setup.ts:37`](../tests/e2e/global-setup.ts#L37)). |

## Phase 4 — Testing coverage and gaps

### Existing coverage

- **Unit:** `tests/unit/booking.spec.ts` covers timezone conversion, custom/unavailable override precedence, DST gaps/folds, notice/horizon, expiry/cancellation capacity semantics, buffers, group capacity, and exclude-current-booking behavior.
- **PostgreSQL integration:** `tests/integration/booking-concurrency.spec.ts` covers same-event capacity-one/group races, simultaneous reschedules, idempotency retries and key mismatch, database-clock expiry, expired confirmation, confirmation races, cancellation release, and failed reschedule preservation. Host-management integration suites cover CRUD, ownership, profile, weekly rules, and overrides.
- **Playwright:** `tests/e2e/booking.spec.ts` covers hold/countdown, invalid guest details, confirmation/duplicate confirmation, management link, reschedule/cancel, capacity release, unavailable slot, expiry, and concurrent idempotent retries. `tests/e2e/host.spec.ts` covers dashboard redirect, invalid login, host CRUD/profile/schedule/override, and responsive rendering. Configuration runs those cases in Chromium/Firefox/WebKit.

### Material gaps

1. **Cross-event host overlap**: no integration test creates two event types for one host and races holds/reschedules into the same instant; this would expose B1.
2. **Host authorization at API boundary**: E2E verifies dashboard redirect and invalid credentials, but does not assert unauthenticated `GET/POST/PATCH/DELETE` responses for every host API. Business-layer ownership tests are not a substitute for route-level cookie enforcement.
3. **Management tokens**: no invalid, malformed-but-well-formed, wrong-case, or canceled-booking token authorization tests; no assertions about PII access after cancel or token revocation/expiry policy.
4. **Timezone UX**: the guest selector is rendered, but Playwright sets browser timezone to UTC and does not switch to a non-UTC timezone then verify date/time labels and selected slot instant. DST conversion is unit-tested, not browser-tested.
5. **Reschedule**: integration tests cover competing capacity and a failed conflict preserving the old slot, but no cases for DST-gap/fold targets, minimum notice/horizon boundaries, buffers, or simultaneous cancel-vs-reschedule.
6. **Notifications**: tests assert a confirmation record but do not independently assert hold, reschedule, guest/host cancellation, or expiry records and payload contents.
7. **Database constraints**: tests do not attempt direct invalid writes for each migration check/unique constraint; schema limits differ from application upper bounds.
8. **Operational scale**: no load/volume test for all-booking reads, idempotency table growth, login brute-force, or repeated hold starvation.
9. **Actual verification in this audit:** `npm test` was run with `RUN_POSTGRES_INTEGRATION=0` to avoid touching any database: **29 unit tests passed; 16 integration tests were skipped by design**. `npm audit` reported 8 moderate dev-only advisories; `npm audit --omit=dev` reported zero. PostgreSQL integration and E2E suites were not rerun because they create/delete test fixtures and this audit was required not to modify a development database. The committed prior QA report records 16 PostgreSQL integration cases and 15 cross-browser E2E runs passed; see [`REQUIREMENTS_AUDIT.md:72`](./REQUIREMENTS_AUDIT.md#L72), [`REQUIREMENTS_AUDIT.md:81`](./REQUIREMENTS_AUDIT.md#L81).

## Prioritized remediation plan

1. **P1 — Define and enforce host-wide overlap semantics.** If the host is a single resource, serialize booking admission/rescheduling on a host-level DB lock and include bookings across the host's event types in overlap checks. Preserve group capacity within one event. Add real-PostgreSQL sequential and simultaneous cross-event hold/reschedule tests.
2. **P1 — Add abuse controls.** Rate-limit login attempts and public hold/confirmation operations, with shared storage suitable for multiple app instances; consider per-IP and per-account throttling and alerting. Keep legitimate retries idempotent.
