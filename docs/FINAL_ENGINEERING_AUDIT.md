# Slotbook Final Engineering Audit

**Audit revision:** `66a31631a757e0d26e7926fbbcb1d4339ac69452`
**Scope:** implementation, database schema/migration, API authorization, scheduling, tests, and submission documents.
**Remediation update:** host-wide overlap protection was implemented after the audit. No application database was modified; PostgreSQL integration tests were added but could not be run without a dedicated test database URL.

## Executive summary

Slotbook uses PostgreSQL transactions for booking state changes. Hold admission and rescheduling now lock the host row before the event and booking rows, preserving per-event capacity while enforcing a shared host calendar across event types. Confirmation rechecks cross-event conflicts before changing state. Database time is used for five-minute expiry, idempotency results are transactionally stored, and booking instants are UTC. The previous QA milestone recorded 16 PostgreSQL integration tests and 15 Playwright cases passing; this remediation did not rerun database-backed suites.

The audited cross-event overlap defect is addressed in the current implementation. A host-level `FOR UPDATE` lock serializes lifecycle operations for that host, and conflict checks compare active bookings from other event types using each type's configured buffers. Public slot listings apply the same rule; transactional hold, confirmation, and reschedule checks remain authoritative. New real-PostgreSQL tests cover simultaneous cross-event requests and lifecycle cases, but have not been executed because no dedicated test database URL is configured.

Security review found no SQL-injection path in the inspected application queries and no unprotected host management handler. The host session cookie is HTTP-only, SameSite=Lax, Secure in production, and signed with an eight-hour expiry. The notable security gaps are missing rate limits on login and public booking endpoints, and long-lived bearer management links that expose guest PII and permit booking changes. These are abuse/privacy concerns, not evidence of an existing account takeover.

## Architecture overview

- Next.js App Router pages and route handlers; Zod validates API inputs.
- Prisma/PostgreSQL models hosts, event types, weekly rules, date overrides, bookings, idempotency records, and notification sink rows. See [`schema.prisma`](../prisma/schema.prisma#L10) and the SQL constraints/indexes in [`migration.sql`](../prisma/migrations/20261105192000_initial/migration.sql#L19).
- [`booking.ts`](../src/lib/booking.ts#L109) generates host-local slots, applies date overrides, notice/horizon limits, DST rules, overlap buffers, and capacity.
- [`booking-service.ts`](../src/lib/booking-service.ts#L75) owns transactional booking lifecycle operations and PostgreSQL row locks.
- Host authentication uses bcrypt and signed stateless cookies in [`auth.ts`](../src/lib/auth.ts#L15); protected API handlers resolve the signed host ID and constrain management operations to that host.
- Unit tests cover pure scheduling/validation/auth logic; PostgreSQL integration tests cover transaction races and host management; Playwright covers real guest and host flows in Chromium, Firefox, and WebKit.

### Verified design properties

- **Transaction/isolation:** booking operations use Prisma interactive transactions; no explicit `SERIALIZABLE` isolation is configured. Each lifecycle mutation locks host → event → booking rows using PostgreSQL `FOR UPDATE`, serializing all booking operations for one host while allowing different hosts to proceed ([`booking-service.ts:75`](../src/lib/booking-service.ts#L75), [`booking-service.ts:85`](../src/lib/booking-service.ts#L85), [`booking-service.ts:91`](../src/lib/booking-service.ts#L91)). Hold creation first locks its idempotency row, then follows that order. No JavaScript mutex is used.
- **Same-event capacity:** hold creation locks the event before reading active same-event bookings and inserting a hold ([`booking-service.ts:292`](../src/lib/booking-service.ts#L292), [`booking-service.ts:304`](../src/lib/booking-service.ts#L304)). Rescheduling follows the same order, excludes its own booking from target capacity, and updates atomically ([`booking-service.ts:473`](../src/lib/booking-service.ts#L473), [`booking-service.ts:501`](../src/lib/booking-service.ts#L501), [`booking-service.ts:521`](../src/lib/booking-service.ts#L521)). Same-event group capacity remains intact.
- **Five-minute holds:** expiry is calculated from PostgreSQL `clock_timestamp()` and set on hold creation ([`booking-service.ts:103`](../src/lib/booking-service.ts#L103), [`booking-service.ts:337`](../src/lib/booking-service.ts#L337)). The integration suite checks remaining time against database time, forces expiry, verifies confirmation rejection, and confirms a replacement can hold the slot ([`booking-concurrency.spec.ts:303`](../tests/integration/booking-concurrency.spec.ts#L303)).
- **Expired/cancelled capacity:** bounded queries include confirmed bookings and held bookings with `expiresAt > now`; conflict calculations ignore cancelled, expired, and elapsed holds ([`booking-service.ts:112`](../src/lib/booking-service.ts#L112), [`booking.ts:221`](../src/lib/booking.ts#L221), [`booking.ts:277`](../src/lib/booking.ts#L277)). Cancellation marks the row cancelled under the host lock, releasing the shared interval.
- **Idempotency:** a unique key is inserted with `ON CONFLICT DO NOTHING`, then selected `FOR UPDATE`; payload hash mismatch returns `409`, while the successful response is written in the same transaction as the booking ([`booking-service.ts:231`](../src/lib/booking-service.ts#L231), [`booking-service.ts:245`](../src/lib/booking-service.ts#L245), [`booking-service.ts:354`](../src/lib/booking-service.ts#L354)). Concurrent retry coverage remains in the suite ([`booking-concurrency.spec.ts:288`](../tests/integration/booking-concurrency.spec.ts#L288)).
- **Confirmation races:** confirmation acquires the host, event, and booking locks, checks expiry and cross-event conflicts, then transitions held to confirmed ([`booking-service.ts:381`](../src/lib/booking-service.ts#L381), [`booking-service.ts:422`](../src/lib/booking-service.ts#L422), [`booking-service.ts:431`](../src/lib/booking-service.ts#L431)). Integration tests cover both duplicate confirmation and conflict against a legacy overlapping booking ([`booking-concurrency.spec.ts:323`](../tests/integration/booking-concurrency.spec.ts#L323), [`booking-concurrency.spec.ts:246`](../tests/integration/booking-concurrency.spec.ts#L246)).
- **Reschedule/cancel:** a failed reschedule throws before update and rolls back, preserving the old interval. Tests cover competing reschedules, rejected cross-event conflicts, and release after a successful move ([`booking-concurrency.spec.ts:220`](../tests/integration/booking-concurrency.spec.ts#L220), [`booking-concurrency.spec.ts:267`](../tests/integration/booking-concurrency.spec.ts#L267), [`booking-concurrency.spec.ts:233`](../tests/integration/booking-concurrency.spec.ts#L233)). Guest and host cancellation use the same host lock before changing booking state. Guest cancellation reason validation remains at [`cancel/route.ts:5`](../src/app/api/bookings/%5Btoken%5D/cancel/route.ts#L5).
- **Timezones and DST:** host windows are resolved through Luxon/IANA zones; booking instants are `TIMESTAMPTZ`, overrides are local `DATE` values ([`schema.prisma:86`](../prisma/schema.prisma#L86), [`schema.prisma:63`](../prisma/schema.prisma#L63)). The slot builder rejects invalid zones/ranges, applies notice/horizon limits, and uses explicit DST candidate resolution ([`booking.ts:58`](../src/lib/booking.ts#L58), [`booking.ts:109`](../src/lib/booking.ts#L109), [`booking.ts:136`](../src/lib/booking.ts#L136)). Nonexistent and ambiguous starts are omitted; tests cover both New York DST transitions ([`booking.spec.ts:73`](../tests/unit/booking.spec.ts#L73)).
- **Buffers and group capacity:** same-event capacity counts seats with the event's buffers; host-wide checks compare the candidate and existing event type's own configured buffers, but only across different event types ([`booking.ts:221`](../src/lib/booking.ts#L221), [`booking.ts:277`](../src/lib/booking.ts#L277)). This preserves group capacity while preventing cross-event overlap.
- **Database constraints:** the migration enforces interval ordering, held expiry presence, positive capacity, range bounds, foreign keys, and relevant unique indexes ([`migration.sql:27`](../prisma/migrations/20261105192000_initial/migration.sql#L27), [`migration.sql:79`](../prisma/migrations/20261105192000_initial/migration.sql#L79), [`migration.sql:80`](../prisma/migrations/20261105192000_initial/migration.sql#L80)). Application bounds are stricter for some fields (e.g. capacity max 100, horizon max 365, notice max 43,200) than database checks. API writes are validated, but direct DB writes can bypass those upper limits; low-risk for this app but worth aligning schema and DB checks.
- **Notifications:** hold, confirmed, rescheduled, and cancelled events are inserted in the booking transaction, so a failed booking transition cannot leave a success-shaped event ([`booking-service.ts:346`](../src/lib/booking-service.ts#L346), [`booking-service.ts:450`](../src/lib/booking-service.ts#L450), [`booking-service.ts:534`](../src/lib/booking-service.ts#L534), [`booking-service.ts:574`](../src/lib/booking-service.ts#L574)). These are DB sink records only; no email is sent. Expiry is the exception in B4.

| Area | Assessment |

| Authentication/passwords | Passwords use bcrypt cost 10 ([`auth.ts:15`](../src/lib/auth.ts#L15), [`auth.ts:19`](../src/lib/auth.ts#L19)). Login normalizes email case, returns generic invalid-credential text, and does not return the password hash ([`login/route.ts:6`](../src/app/api/auth/login/route.ts#L6), [`login/route.ts:26`](../src/app/api/auth/login/route.ts#L26)). No signup/password reset is implemented; the seeded host is the intended account path. |
| Session signing/expiry/logout | Host ID plus expiry is HMAC-SHA256 signed and verified using constant-time equality; expiry is eight hours ([`auth.ts:5`](../src/lib/auth.ts#L5), [`auth.ts:23`](../src/lib/auth.ts#L23), [`auth.ts:30`](../src/lib/auth.ts#L30)). Logout clears the cookie ([`logout/route.ts:6`](../src/app/api/auth/logout/route.ts#L6)). Sessions are stateless: there is no per-session revocation or password-change invalidation before expiry; secret rotation invalidates all sessions. |
| Host authorization | Inspected host event, profile, availability, and override handlers all resolve a signed session and return `401` when absent; service queries include the authenticated `hostId`. Host cancellation separately verifies the signed session and compares the booking owner ([`host-session.ts:4`](../src/lib/host-session.ts#L4), [`host cancel route:18`](../src/app/api/host/bookings/%5Bid%5D/cancel/route.ts#L18), [`booking-service.ts:586`](../src/lib/booking-service.ts#L586)). No missing authorization path was found in the enumerated protected routes. |
| Guest management token | A random booking UUID is HMAC-derived with the server secret; only SHA-256 token hash is stored ([`auth.ts:50`](../src/lib/auth.ts#L50), [`auth.ts:54`](../src/lib/auth.ts#L54), [`booking-service.ts:329`](../src/lib/booking-service.ts#L329)). **Medium privacy risk:** the token is a bearer credential in the URL, has no expiry/revocation separate from the global secret, and grants access to the guest name/email plus reschedule/cancel while confirmed ([`bookings/[token]/page.tsx:13`](../src/app/bookings/%5Btoken%5D/page.tsx#L13), [`bookings/[token]/page.tsx:43`](../src/app/bookings/%5Btoken%5D/page.tsx#L43)). No explicit Referrer-Policy is configured in `next.config.ts`; no evidence of an external analytics/referrer sink was found. |
| CSRF | No CSRF token or Origin validation is present. The host cookie is SameSite=Lax and state-changing management endpoints parse JSON, which blocks ordinary cross-site HTML form submissions from providing valid bodies. No high-impact CSRF exploit was identified in the inspected routes. Logout is a form POST and has no origin check, so cross-site forced logout is a possible low-impact nuisance. Add an Origin check/CSRF defense as defense in depth if the app gains cookie-authenticated form or non-JSON mutations. |
| Validation/error handling | Booking, host settings, and management inputs are Zod-validated; most errors map to explicit 400/401/404/409 responses. Generic login errors avoid direct account enumeration through message differences. Payloads are not consistently `.strict()` across every route, but Zod strips/ignores unrecognized fields rather than passing them to Prisma. Request body size limits are not configured in application code. |
| SQL injection/Prisma | No injection path was identified. Application raw queries use Prisma tagged templates; ordinary reads/writes use parameterized Prisma methods. The E2E setup has one `$executeRawUnsafe` call with a fixed literal schema statement, not user-controlled input ([`global-setup.ts:37`](../tests/e2e/global-setup.ts#L37)). |
| Rate limiting/abuse | **Medium security/availability gap:** login has no throttling, lockout, or challenge; each valid-shape attempt can invoke bcrypt ([`login/route.ts:11`](../src/app/api/auth/login/route.ts#L11), [`login/route.ts:26`](../src/app/api/auth/login/route.ts#L26)). Repeated password guesses can consume CPU; an attacker can repeatedly occupy offered capacity with short-lived holds. This is a realistic denial-of-service/password-spraying opportunity, though holds self-expire after five minutes. |
| Sensitive data/logging | Login responses contain only host ID/name. The management page intentionally returns guest name/email to a bearer-token holder; notification rows also retain guest PII in PostgreSQL. No explicit application logging of passwords, tokens, or request bodies was found in inspected paths. Production DB/log retention and access controls are deployment responsibilities not verified here. |

Runtime/framework/proxy defaults were not independently tested, so this is a hardening gap rather than a claimed exploitable vulnerability. |

## Phase 4 — Testing coverage and gaps

### Existing coverage

- **Unit:** `tests/unit/booking.spec.ts` covers timezone conversion, custom/unavailable override precedence, DST gaps/folds, notice/horizon, expiry/cancellation capacity semantics, buffers, group capacity, and exclude-current-booking behavior.
- **PostgreSQL integration:** `tests/integration/booking-concurrency.spec.ts` covers same-event capacity-one/group races, simultaneous reschedules, idempotency retries and key mismatch, database-clock expiry, expired confirmation, confirmation races, cancellation release, and failed reschedule preservation. Host-management integration suites cover CRUD, ownership, profile, weekly rules, and overrides.
- **Playwright:** `tests/e2e/booking.spec.ts` covers hold/countdown, invalid guest details, confirmation/duplicate confirmation, management link, reschedule/cancel, capacity release, unavailable slot, expiry, and concurrent idempotent retries. `tests/e2e/host.spec.ts` covers dashboard redirect, invalid login, host CRUD/profile/schedule/override, and responsive rendering. Configuration runs those cases in Chromium/Firefox/WebKit.

### Material gaps

1. **Cross-event host overlap**: PostgreSQL integration cases now race holds across event types and cover conflict release/confirmation/reschedule behavior, but require execution against the isolated integration schema before being verified.
2. **Host authorization at API boundary**: E2E verifies dashboard redirect and invalid credentials, but does not assert unauthenticated `GET/POST/PATCH/DELETE` responses for every host API. Business-layer ownership tests are not a substitute for route-level cookie enforcement.
3. **Management tokens**: no invalid, malformed-but-well-formed, wrong-case, or canceled-booking token authorization tests; no assertions about PII access after cancel or token revocation/expiry policy.
4. **Timezone UX**: the guest selector is rendered, but Playwright sets browser timezone to UTC and does not switch to a non-UTC timezone then verify date/time labels and selected slot instant. DST conversion is unit-tested, not browser-tested.
5. **Reschedule**: integration tests cover competing capacity and a failed conflict preserving the old slot, but no cases for DST-gap/fold targets, minimum notice/horizon boundaries, buffers, or simultaneous cancel-vs-reschedule.
6. **Notifications**: tests assert a confirmation record but do not independently assert hold, reschedule, guest/host cancellation, or expiry records and payload contents.
7. **Database constraints**: tests do not attempt direct invalid writes for each migration check/unique constraint; schema limits differ from application upper bounds.
8. **Operational scale**: no load/volume test for bounded booking reads, idempotency table growth, login brute-force, or repeated hold starvation.
9. **Actual verification:** the original audit ran `npm test` with `RUN_POSTGRES_INTEGRATION=0`: 29 unit tests passed and 16 integration tests were skipped. For this remediation, `npm run lint` passed; two runs of `npm test`/`npm run test` each passed 32 unit tests and skipped 26 PostgreSQL integration tests; `npm run build` passed. PostgreSQL integration and Playwright E2E tests were not run because no dedicated `E2E_DATABASE_URL` is configured; their runners refuse to fall back to `DATABASE_URL`. The development database was not modified. ## Prioritized remediation plan
